# board-test

ESP32-S3 N16R8 + OV2640 の基板用。ESP-IDFのファームと、Python/TkinterのGUI。Dev / camera-main とは別物。

## 使い方

```powershell
.\start-gui.ps1            # GUI起動
.\flash.ps1                # GUIを切断してから。ビルド→書き込み→照合→再起動
.\flash.ps1 -Port COM14
```

ルートの `./write-firmware.ps1` でも同じ。ESP-IDFは `IDF_PATH` → `~/esp/esp-idf` の順に探す。ESP32-S3が1台だけつながっていればCOMも自動で見つける。複数なら `-Port`、別のIDFなら `-IdfPath`。実行ポリシーで止められたら `powershell -NoProfile -ExecutionPolicy Bypass -File .\write-firmware.ps1`。

GUIでCOMを選んで接続（うちだとCOM14）。初回は `.venv` を作ってPillowとpyserialを入れる。

書き込めないとき: BOOT(SW2)を押したままEN(SW8)を押して離し、BOOTを離してから書き込む。終わったらENを押して通常起動。

## 撮影

起動するとSDをチェックして、露出と色が落ち着くまでフレームを捨てる。緑のReadyが点いたらGUIの「撮影・SD保存」かSW6で撮れる。

- 標準: 1600x1200、JPEG品質12、XCLK 20MHz
- 保存先: `/DCIM/CAMERA/S0000001/IMG00001.JPG` から連番
- `.TMP` に書く → flush/fsync → 読み戻してサイズとCRCを確認 → `.JPG` にリネーム
- 既存のファイルは上書きしない。途中で止まった `.TMP` は消さずに残す
- PCに送ったJPEGもSDのCRCと比べる
- SDのフォーマット機能はない

画像は基板側で180度回している。GUIの向きは初期値「そのまま」で、PCにはそのままのJPEGを保存。GUIで向きを変えたときだけ再圧縮する。

GUIは幅に合わせて3列/2列/1列。狭いときはスクロール（ホイールで縦、Shift+ホイールで横）。

## LED

緑=今どうすればいいか、赤=失敗、オレンジ=モード番号。どのモードでも同じ。

| 緑 Ready | 意味 |
|---|---|
| 点灯 | 準備OK。静止画ならSW6で撮影、動画ならSW6で録画開始、モード7ならスマホからつなぐ |
| ゆっくり点滅 (1秒) | 準備中・処理中。待つ |
| 速い点滅 (0.25秒) | 録画中。SW6で停止 |
| 消灯 | モード選択中（SW7で確定、SW6でキャンセル）か停止中（赤が点滅） |

| 赤 Error | 意味 |
|---|---|
| 消灯 | 問題なし |
| 点灯 | 直前の撮影・録画の保存に失敗。次に成功すれば消える |
| 点滅 | 準備に失敗して停止中（SDなし、カメラ、Wi-Fiなど）。直してSW6かGUIの「再準備」 |

オレンジ3灯はモード番号（選択中は候補）を2進で表示。点滅はしない。

## モード

SW7でモード選択に入って、RV1で0〜7を選び、SW7で確定。SW6でキャンセル。モードはNVSに保存するので再起動しても残る。

| 番号 | 3灯 | モード | 内容 |
|---|---|---|---|
| 0 | 000 | 標準 | 1600x1200、品質12、ゲイン上限2倍 |
| 1 | 001 | 高精細 | 1600x1200、品質8 |
| 2 | 010 | 連写 | 5枚撮ってから順にSDへ保存 |
| 3 | 011 | セルフタイマー | 10秒後に撮影。待っている間は緑が速く点滅、SW6で中止 |
| 4 | 100 | タイムラプス | 2秒に1コマ、MJPEG/AVI（10fps再生で20倍速）。最大60分 or 約240MB |
| 5 | 101 | 暗所 | 800x600、ゲイン上限8倍、露出も暗所向け |
| 6 | 110 | 動画 | 640x480、MJPEG/AVI、音声なし（マイクがない） |
| 7 | 111 | スマホ転送 | Wi-Fi APを出してブラウザで写真・動画を見る |

鮮やか・白黒・セピアは基板のモードからは外して、スマホの拡大画面とGUIの「加工」で保存するときにかける。SDに入るのは常に元のJPEG。スマホでの加工は1枚1秒くらい。

JPEG品質は数字が小さいほど圧縮が弱い。解像感が上がるわけではない。暗所モードはノイズとブレが増える。

### モード切替の待ち

- 静止画系（0〜3, 5）同士と、4→6 はカメラを再起動せず設定だけ変える。すぐ終わる
- 静止画⇔動画、起動時より大きい解像度への切替（暗所で起動して標準にする等）、モード7からの復帰、電源ON はカメラ再起動で10秒くらい
- 短い方で安定しなかったら自動で再起動の方に切り替わる

### 動画

SW6で開始、もう一度SW6で停止。録画中は緑が速く点滅、停止後の保存中はゆっくり点滅。録画中はSW7でのモード変更不可。最大5分 or 約240MBで自動停止。

保存先は `/DCIM/CAMERA/S0000001/VID00001.AVI` から。録画中は `.TMP` に追記して、止めたらAVIヘッダーとインデックスを書き、JPEG部分のCRCを確認してから `.AVI` にリネーム。電源が落ちて残った `.TMP` は消さないし直さない。照合が終わるまで電源は切らない。

GUIからもモード変更と録画の開始・停止ができる。「動画をPCへ保存」は最後の動画をUSBで取ってCRCを確認してから保存する。転送中は基板を触らない。再起動すると最後の動画の情報は消えるけど、SDには残っているのでカードから取り出せる。録画後にGUIに出る画像は最初のフレームで、ライブ表示ではない。

## 配線

| 対象 | GPIO | |
|---|---|---|
| Ready 緑 | 46 | |
| Error 赤 | 38 | |
| Mode オレンジ | 45 / 21 / 1 | 4 / 2 / 1 の2進 |
| SW6 / SW7 | 47 / 48 | SW6: 撮影・録画・キャンセル・再準備、SW7: モード選択 |
| RV1 | 2 | ADC |
| microSD (SPI) | CS 10 / MOSI 11 / SCLK 12 / MISO 13 | |

LEDはLOWで点灯。GUIに出るのはGPIOの状態で、実際に光っているかはわからない。Modeの3灯は手動でON/OFFできない。SW6/SW7は別タスクでデバウンスしていて、撮影中も数えている。

RV1(10k)にR16(10k)が直列なので最大でも約1.65V、ADCは半分くらいまでしか行かない。回路どおり。生値は4095基準のまま、メーターの上限を2048にしている。「取得値を最大に設定」はGUIを閉じるまで有効。

RV1の読み方: 20msごとに5回読んで中央値、ローパス、32カウントのヒステリシス、約200ms安定したら確定。選択に入った直後は番号を変えず、48カウント以上動かしてから追従する。デバウンスはSW7 約60ms、SW6 約30ms。

## 画質の調査メモ (2026-10-17)

### 起動直後の色

起動直後に暗くて緑っぽい画像になるのが毎回出る。20MHzだと最初の画像は0.27秒くらいで出るけど、明るさと色が落ち着くのは2〜3秒後。最初の数枚を捨てるだけだと足りないので、今は

- 最低4秒・12フレーム
- JPEGをデコードして平均輝度とRGB比が続けて安定するまで待つ
- 25秒以内に安定しなければ準備失敗

にしている。デコードする分、準備は4秒より長くなる。

### XCLK・ゲイン

- XCLK 10MHzは横ノイズが増えた、16MHzはフレーム取得がタイムアウト → 20MHz
- 50Hzバンディング設定は効果がはっきりしなかったので標準のまま
- ゲイン上限 2/4/8倍 を2枚ずつ比較。2倍でも平均輝度111くらいあって、暗部の行方向のばらつき（隣接行平均の二階差分）は 2倍 6.3 / 4倍 14.9 → 2倍にした。露光が長くなるので動くものはブレやすい

測定は `gui/characterize.py` と `gui/compare_gain.py`（撮影設定を一時的に変える）。結果は `captures/` に置いている。

### 速度

CPU 240MHz、PSRAM 80MHz、`-Os`、TCPバッファ16KBにした（前は160MHz / 40MHz / `-Og` / 5760バイト）。動画の100ms間隔は取得とSD書き込みの時間込みにした（前は処理後にさらに100ms待っていた）。目標10fpsだけど暗いとSDや露光で落ちる。

変更後の準備時間は 9247 / 11341 / 9726ms、変更前は 13084ms（1回だけ。露出待ちの影響があるので厳密な比較ではない）。ファームサイズは 1,028,624 → 937,792 バイト。

### exFAT

刺さっていた8GBのカードがexFATで、IDFの標準設定だとマウントできなかった。プロジェクト内にfatfsをコピーしてexFATを有効にした（IDF本体はそのまま）。詳細は `firmware/components/fatfs/LOCAL_CHANGES.md`。

## 横縞の除去 (2026-10-20)

暗いところに出る青・オレンジの細い横縞。レンズを覆っても毎回同じ行に出る（撮影ごとの相関0.9）。OV2640内部の処理の8行単位にそろっていて、レジスタをいじっても消えなかったので、静止画（標準・高精細・連写・セルフタイマー・暗所）は保存したあとに基板上で消すことにした。

- 撮影したらセンサーのJPEGをそのままSDに保存してPCにも出し、すぐReadyに戻る
- 撮影の合間に裏で処理する。コア1がJPEGの展開と再圧縮、コア0が行ごとのずれの推定と補正。どちらも優先度1なので撮影・USB・Wi-Fiは邪魔しない
- 結果は `.CLN` に書いてCRCを確認してから元のJPGと入れ替える。入れ替えるまで元のJPGは残る
- 2コアでやった結果と1コアでやった結果はバイト単位で一致（`grab` に `clean:true, verify:true` で確認）
- 補助タスクは各コアに常駐。写真ごとに作って消すと、消したタスクに通知が飛んで解放済みメモリを触るため
- 縞の量はリニアな光量で推定する。トーンカーブはこの基板のOV2640で実測（2026-10-21、`row_noise.h` の表）。ゲイン1倍・WB固定で露光を4〜1200まで振ってDebevec & Malik法で緑チャンネルから出した。黒は5くらい、80くらいまではほぼ直線
- 行の基準は上下48行（自分を含む97行）の、横16区間ごとの平均の中央値。縞は8行〜数十行の帯で出るので、平均を基準にすると帯の隣の行が逆向きに補正されて（暗部が紫になる）、窓が狭いと太い帯が残っていた。中央値なら全幅の段差やなだらかな明暗はそのまま残る
- 縞はセンサーのレンズ補正（周辺ほどゲインを上げる）より前に乗っているので、画像の左右の端では中央の2倍くらい強い。`1+1.7r²`（中心は横0.55・縦0.5、rは横幅の半分で正規化）で割って推定し、掛けて引く。レンズ補正（DSPのCTRL1 bit1）を切ると縞は横に平らになり、当てはめもゲイン0になった（2026-10-21）
- 撮ったフレームはすぐPSRAMにコピーして、保存・送信・縞除去は全部コピーから。ドライバが数秒持ったままのバッファを次のフレームで上書きすることがあって、画像の下の方が壊れたため
- 横16区間の半分以上がそろってずれている行だけ消す。机の端みたいに半分より短い横線は残す（画面の半分以上を横切る細い線は消えることがある）
- 黒や白に張り付いた部分は情報がないので、暗部の太い帯は完全には戻らない
- 処理前に電源を切った写真は縞ありのまま。GUIやPCに送る画像も縞除去前（SDの方は数秒後に差し替わる）
- モード7に切り替えるときは残りの処理を待つ。動画・タイムラプス中は新しく始めない（録画開始時は処理中の1枚を待つ、最大6秒くらい）。連写は前の処理が終わってから撮り始める
- 状態取得の `cleanup_pending` / `cleanup_done` / `cleanup_failed` で進み具合がわかる

1枚あたり: 撮影からReadyまで約2.0秒、縞除去 5.1秒（展開1.7 / 推定1.0 / 補正+圧縮2.5）、SDの入れ替え 1.9秒。

行方向のばらつき (Y / Cb / Cr、±6行の中央値との差) は、実機の `grab clean:true` で 3.8 / 5.6 / 3.8 → 1.1 / 0.7 / 1.0（前の方式だと同じような場面で 1.9 / 1.1 / 1.2）。再圧縮は4:2:2、品質90（高精細は94）。JPEGライブラリと本体は `-O2` にしたので、カメラドライバのタスクスタックを4KBにした（2KBだとあふれる）。

### SDのクロック

SPIを4MHz → 20MHzにした。19枚の保存・CRC確認・縞除去が全部通って、保存は 1.6秒 → 0.95秒、入れ替えは 3.0秒 → 1.8秒。起動時のSDチェックが20MHzで失敗したらその起動中は4MHzに戻す。今の値は状態取得の `sd_khz`、変えるときは `sd_speed`。

20MHzで動画と転送も確認。640x480で20秒録って182コマ（4MHzだと128コマ）、ffmpegでエラーなし。モード7で写真と動画(3.76MB)を510〜610KB/sくらいで取れた。

### 診断コマンド

- `reg` … センサーのレジスタ読み書き
- `expose` … `value` と `gain` で露光とゲインを固定、WBも止める。引数なしで自動に戻す
- `grab` … SDに保存せず取得。`clean:true` で除去前後を比べられる

縞除去のホストテストは `firmware/test_row_noise.c`。

## 電源まわり（次の基板で検討、未検証）

縞は根本的にはセンサー電源のノイズだと思っている。回路図 esp32_camera_v2 を見て気になったところ:

- 2.8V（U2 S-817B28AMC、出力C2 1µF）: ESP32・microSD・LEDと同じ3.3V(U4)から作っている。S-817は低消費電流タイプでリップル除去が弱い。PSRRの高いLDOにして、入力にフェライトビーズ+コンデンサを入れたい
- 1.2V（U3 TPS77012、50mA、出力C4 4.7µF）: UXGA時のOV2640のコア電流に足りているかデータシートで確認。足りなければ150mA以上のLDO
- J5まわり: 0.1µFがC8の1個だけ。2.8V / 1.2V / 3.3V(DOVDD) それぞれにピンの近くで 0.1µF + 1〜10µF ほしい

作り直す前に試すなら、オシロで撮影中の2.8Vと1.2Vのリップルを見る。それかC2・C4に10µFを足すか、2.8Vだけ外部電源から入れて、`grab` で縞の量を比べる。減れば電源が原因。

## スマホで写真を保存（モード7）

1. SW7 → RV1で111(7) → SW7
2. スマホで `Camera-` で始まるWi-Fiにつなぐ。パスワードは `12345678`（GUIにもWi-Fi名と一緒に出る）
3. Safari / Chromeで `http://192.168.4.1` を開く。「インターネットなし」と出てもつないだままにする
4. 「撮影フォルダ」を選んで写真をタップ。iPhoneなら拡大画像を長押し →「写真に保存」。「画像を開く」から共有でもいい。「ファイル保存」は普通のダウンロード。動画タブからAVIも取れる

- 一覧は新しい順に24件ずつ、「さらに表示」で続き
- 転送モード中はカメラを止めて、SDはHTTP側だけが読む
- スマホから削除もできる（「選択」で複数、拡大画面のゴミ箱、動画の詳細）。確認が出て、SDから完全に消える
- 消せるのはファームが作ったIMG/VIDだけ。TMPやフォルダは不可。削除は専用ヘッダー付きのPOSTだけ受ける
- アップロードとフォーマットはない
- モードを戻すとHTTPとWi-Fiを止めてSDを解放してから撮影準備。転送中にモードを変えるとダウンロードは切れる
- モード7ではSW6とGUIのシャッターは効かない

Wi-FiはWPA2-PSK / CCMP、最大3台。ページは全部基板の中にあって外部には取りに行かない。写真は再圧縮しない。

Safariから写真アプリへの自動保存はできないので、長押しか共有で保存する。Web Share APIはHTTPだと使えないので使っていない。

## フォルダとURL

APのIPは 192.168.4.1 / 255.255.255.0 で固定。再起動してもモードを変えても `http://192.168.4.1/`。

SDを最初にマウントしたときに `/DCIM/CAMERA/S0000001` のような新しいフォルダを作る。同じ起動中は静止画も動画も同じフォルダ、再起動すると次のフォルダ。NVSとSDの両方を見るので、古いフォルダを再利用することはない。何も撮らなかった起動の空フォルダは一覧に出さない。日付は付けない。

前のバージョンでSD直下に保存したファイルはそのまま。「これまでの写真」から見られる。フォルダは64件ずつ読み込み、「さらに古い撮影フォルダ…」で追加。

## パーティション

2026-10-18 にアプリ領域を1MB → 3MBにした（`firmware/partitions.csv`）。nvs (0x9000) と phy_init (0xF000) は同じ位置なので、モード・Wi-Fiパスワード・フォルダ番号はそのまま引き継がれる。

書き換える前のフラッシュは `backups/` に吸い出してある（gitには入れていない）。

- 先頭1MB: `before_board_test_20261017_first1mb.bin`
- 0x100000〜0x10FFFF: `before_ap_20261017_100000_10ffff.bin`
- 0x110000〜0x30FFFF: `before_app3mb_20261018_110000_30ffff.bin`
